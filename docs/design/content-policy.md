# ModelSphere 官网内容与证据规范

| 属性 | 内容 |
| --- | --- |
| 更新日期 | 2026-10-21 |
| 状态 | 当前全站设计说明；文档试点已实现，其他模块待实施与验收 |
| 上游规范 | [组件契约](components.md)、[页面契约](page-contracts.md) |
| 范围 | 内容模型、技术声明、来源记录、发布状态、修改与撤回 |

本规范定义博客与官网文案、Catalog 数据引用、开发者文档的内容和证据要求。网站文案和博客由 Git 维护，文档从独立仓库同步，Catalog 保留其数据源；网站内容统一发布。设计稿、截图和示例不是业务事实证据。

内容的“审核”表示对内容与证据作出明确确认，记录在 PR 或受控发布记录中，可由作者本人完成，不额外要求第二人审批；仍遵守实际仓库权限与分支保护，程序校验不代替事实确认。

## 1 内容决策

| 编号 | 提案 | 结果 |
| --- | --- | --- |
| E01 | 内容状态与技术验证状态分离 | 已发布的配方仍可以明确标为实验性或未验证；不能把上线等同于生产验证 |
| E02 | 模型配方、测评、文章、指南和技术声明使用独立记录 | 页面引用记录 id，不各自复制技术事实和性能数字 |
| E03 | 性能展示必须能追溯到测试条件和原始结果 | 首页数字由审核过的测评记录映射，浏览器不重新计算宣传结论 |
| E04 | 发布只输出已审核内容，预览示例与正式数据分开 | 草稿、示例、审核信息不进入公开页面、搜索索引或前端数据包 |
| E05 | 发布前校验结构与来源，事实判断由明确的审核记录承担 | 链接可访问和 JSON 格式正确都不能代替技术核实 |

## 2 Git 内容与发布状态

官网文案、Article、Claim、Evidence、Media 和页面配置以仓库文件维护；文章正文使用 Markdown，页面配置和证据使用受校验的结构化文件。版本以完整 Git commit 追溯，不另建数据库 revision。Catalog 保留源版本；开发者文档保留来源仓库 commit。

| 字段 | 类型或取值 | 约束 |
| --- | --- | --- |
| `id` | string | 公开标识，稳定且唯一；小写字母、数字与单连字符 |
| `updatedAt` | 带时区的 RFC 3339 时间 | 内容实际修改时间，不随构建自动改变 |
| `publishedAt?` | YYYY-MM-DD | 文章首次发布日期；正式文章必填，修订保留原值；不接受未来日期定时发布 |
| `evidenceIds` | string[] | 引用可核查来源；无事实主张的导航文字可为空 |
| `draft?` | boolean | 草稿标记；正式构建在内容插件之前排除，不能只从列表隐藏 |

“草稿”“可发布”“已上线”“已撤回”分别由工作分支/草稿标记、明确的预览确认、部署记录和撤回提交判断，不信任作者在 frontmatter 中自行声明已批准或已上线。审核人、确认时间和提交 SHA 记录在 PR/发布系统，不进入公开页面与数据包。

1. 新内容在工作分支维护，补齐正文、元数据、图片和来源；本地预览只用于排版。
2. PR 对完整站点进行检查和预览。内容改变后重新检查，不能沿用旧 SHA 的确认。
3. 合并后针对实际提交重新构建正式候选、核验并发布；成功切换前，线上仍是上一次健康版本。
4. 已上线文章的新草稿留在工作分支；不得将主分支原文覆盖成草稿导致另一篇文章发布时意外撤下它。
5. 撤回通过明确的 Git 变更使内容退出可发布集合，清理推荐、默认项和相关引用，重新构建网站；恢复也需新变更与检查。

### 2.1 来源锁定与产物

网站提交固定代码、博客、页面配置、素材和文档源锁定文件。文档源以仓库、完整 commit 与内容子目录追溯；Catalog 基线以数据版本和 hash 追溯。正式候选绑定这些输入和镜像 digest，门户、博客、文档共同发布和回滚，Catalog 实时版本独立更新。

只有合格正文和其引用资源进入生成目录；未发布图片不能因放进 `static/` 就被公开。原始仓库目录、内部审核记录、测试 fixture 和构建日志不复制到网站。Git 历史不提供保密能力，私密资料不能提交到公开仓库。

## 3 来源与技术声明

### 3.1 来源记录

来源表独立于内容记录，字段如下：

| 字段 | 规则 |
| --- | --- |
| `id`、`label` | 来源唯一标识与可读名称 |
| `kind` | code / documentation / benchmark-report / pull-request / release / owner-confirmation |
| `publicHref` | 可公开访问的来源页面或站内资料地址，必须支持定位相关内容 |
| `locator` | 章节、文件与行号、测试记录编号或 PR 关键位置，不能只指向一个巨大仓库首页 |
| `sourceRevision?` | 代码使用完整提交 SHA；文档使用版本或日期；稳定报告使用报告版本 |
| `checkedAt` | 最近核对时间，带时区 |
| `checkedBy` | 执行核对的人或工具标识，区别于内容批准人 |
| `checkResult` | supports / does-not-support / inaccessible |
| `scope` | 来源能够支持的具体结论和限制 |

`supports` 表示核对到相关内容，不等于整条官网声明已经获批。代码证据必须固定到提交；可变网页应记录核对日期和章节。私有链接、临时签名下载 URL、本机路径和聊天记录不能作为公开证据入口；需要先形成可公开核查且经过授权的摘要或报告。

来源适用范围：

- 代码能支持实现机制，不能单独证明吞吐提升或生产稳定性。
- 测试报告仅支持报告列出的环境、工作负载和结果。
- 已合并 PR 能支持上游合并事实，不能推出已进入所有发布版本。
- 项目负责人确认可支持项目定位或负责范围，不能代替可复现性能报告。
- Stitch、截图、占位内容和生成器输出仅是设计参考，不是业务事实证据。

### 3.2 技术声明记录

首页特性、架构层次、机制说明、上游贡献和生态关系使用 Claim 记录，继承公共字段，补充：

| 字段 | 规则 |
| --- | --- |
| `text` | 准备展示的事实陈述 |
| `kind` | capability / architecture / contribution / compatibility / roadmap |
| `implementation` | available / experimental / planned |
| `scope` | 适用版本、引擎、硬件或场景；不能省略关键前提 |
| `limitations` | 限制列表；没有已知限制时为空，不写“无限制” |
| `evidenceIds` | 至少一项支持当前声明；roadmap 可用公开的路线图或计划说明 |

planned 必须展示“规划中”，experimental 展示“实验性”；两者不能混写成现有生产能力。引用配方、测试或贡献时，声明范围不能大于其来源。涉及百分比、倍数或延迟的声明还必须引用 Benchmark，不能只挂代码链接。

架构图节点、首页能力卡和正文使用相同声明记录或其受控摘要；不得在图中把 planned 节点画成“已上线”。

## 4 Catalog 模型与配方

Catalog 的模型、配方、测评与版本历史均由其源系统维护。官网适配器把来源协议映射为展示 DTO，保留原始稳定标识、数据版本、配方版本和报告引用；不得要求源数据满足网站的人工确认字段或在网站仓库复制成第二套权威编辑源。

| 展示信息 | 映射与缺失规则 |
| --- | --- |
| 模型 | 稳定 id、名称、家族、说明及来源；名称不能作为唯一标识 |
| 配方 | 所属模型、配方 id、版本、引擎与版本、硬件、标签、拓扑、部署配置或说明入口 |
| 运行约束 | 精度、量化、并行方式、上下文及适用环境按来源提供；缺失不猜测 |
| 历史 | 源版本及对应 commit/不可变引用；不由官网生成虚假历史 |
| 结果 | 基线与优化记录、指标、条件、报告引用；不得混用不同数据版本 |
| 技术验证状态 | 仅在源记录或证据支持时展示“所列环境已验证／实验性／未验证”；来源无此字段时省略徽标或写“未提供验证信息” |

硬件、家族、引擎、标签与拓扑筛选从 Catalog 字段映射；URL 使用稳定标识。模型卡跳到模型详情，配方入口跳到配方与版本页。仅有配方不表示有性能成绩，一次运行成功也不能宣称生产验证。

目录搜索索引从同一 `dataVersion` 提取模型名称、简介、稳定标识、配方名称、容器镜像引用和硬件名称；来源缺失的字段不补造，也不从部署脚本全文推断。模型视图匹配任一所属配方后只返回一次模型，配方视图只返回实际匹配的配方。硬件筛选仍使用来源稳定标识，搜索硬件名称不改变多选筛选语义。

本期目录的 `improvement-desc` 按最新测量版本所记录负载的最大百分比排序。界面使用“吞吐量提升”“最佳负载提升”等直接描述指标的标签，保留负载、测量版本和报告入口；不在卡片、详情或表格中重复强调来源、添加免责段落或解释内部数据处理。无值置后，不以 0 补齐，同值按稳定 id。模型视图不挑选最大提升作为模型代表。统计卡的样本与计算规则见工程清单；官网若发布同条件性能结论，仍必须满足下节测试证据要求。

首页配置或博客引用 Catalog 时保存 `sourceId`、`sourceVersion`、必要的 `recipeVersion`、公开证据地址和受控摘要。源记录变化不会自动改写已发布宣传结论；撤销或失效来源需复核相关引用。

## 5 性能测评

Catalog 测评保留源 schema。以下是官网发布性能结论时要求核对的证据分组，由适配器和编辑校验，不是在网站仓库另建权威 Benchmark 集合。原始报告资料不完整时可提供真实入口并标记缺失；不得生成提升宣传或用零补齐未知值。

| 分组 | 必填内容 |
| --- | --- |
| 标识 | `title`、`model`（同配方模型结构）、`recipeId?`、`testedAt` |
| 环境 `environment` | 节点数、加速器型号与数量、单卡显存及单位、CPU、主存、操作系统、驱动、运行时与引擎版本；多节点时补网络类型和带宽 |
| 配置 `configuration` | 权重精度、量化方式、并行策略、缓存开关、关键调度参数、固定版本的配置来源 |
| 工作负载 `workload` | 数据集或生成方法、输入输出 token 长度或分布、并发或请求到达模型、请求总数、流式开关 |
| 方法 `method` | 测试工具与版本、运行命令、预热方式、计时边界、重复次数、聚合方法、失败请求处理方式 |
| 结果 `results` | 至少一个指标；错误请求数、总请求数、各次运行结果与原始记录入口 |
| 结论 `summary` | 条件限定、观察结果、限制；不得扩大到未测试环境 |
| 来源 `evidenceIds` | 至少一个公开测试报告或可核查结果来源 |

字段不适用时明确写“不适用”及原因，不用零代替未知值。重复次数至少为 1；只有一次运行时必须注明“单次测量”，不能给出跨次波动或显著性结论。

指标结构：

| 字段 | 规则 |
| --- | --- |
| `id`、`label` | 指标标识与名称，例如 TTFT，但不预置成绩 |
| `value` | 有限数值，不接受 NaN、Infinity 或带单位字符串 |
| `unit` | ms / s / tokens/s / requests/s / % / count |
| `statistic` | mean / median / p90 / p95 / p99 / total / rate |
| `scope` | per-request / per-user / per-device / aggregate |
| `definition` | 计算口径、是否包含排队、是输入还是输出 token 等 |
| `displayDecimals` | 0 至 3，按测量精度指定，不补造有效位数 |

TTFT、总延迟、每用户输出速度和集群总吞吐不得互换名称。所有图表和表格来自同一 results，不能单独手填另一份数据。

比较结果额外要求：

- 保存 baseline 与 candidate 的各自环境、配置、运行记录，以及 `changedFactors`。
- 同模型版本、同负载、同指标口径是提升比较的必要条件；硬件不同只能标注为不同环境结果，不称为同条件提升。
- 提升公式、原始值和方向必须明确：吞吐增长为 `(candidate / baseline - 1) × 100%`；延迟降低为 `(baseline - candidate) / baseline × 100%`；baseline 必须大于 0。
- 保留未舍入数值用于计算，展示时才按 displayDecimals 格式化。
- 内容构建阶段校验预先审核的计算结果；首页只引用已核对的展示值和测评 id，不在浏览器重新生成“提升 X 倍”的文案。
- “达到基线 2 倍”与“提升 100%”可等价；禁止使用含义不明确的“提升 2 倍”。

MetricCard 由明确的测评 id 和指标 id 派生 valueText、unit、context、evidence；BenchmarkTable 由同一测评派生行列。不能以网页加载时间或动画数值伪装为实测。

## 6 博客与开发者文档

### 6.1 文章

Article 继承公共字段，包含 `title`、`summary`、`kind: internal / external`，以及可选 `author`、`categoryId`、`tagIds`、`technicalKeywords`、`pullRequestRefs`、`cover`、`readingMinutes`、`relatedIds`。

- internal 必须有唯一 slug 与非空正文；slug 匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`，链接由 `/blog/{slug}` 派生。
- external 必须有真实原文链接，不生成本站空详情，也不复制全文作为默认展示。
- relatedIds 最多 3 项，必须为其他已发布文章，不能重复或引用自身。
- 作者未提供则不展示；readingMinutes 首期只接受有来源的作者标注，未提供则省略。
- 技术数字、能力声明和上游贡献引用对应 Benchmark 或 Claim；不能仅靠文章发布日期使未经核实的结论生效。
- 分类字典的 id 与显示名称分离；发布日期展示为 YYYY-MM-DD，修改文章不改变首次发布日期。
- `tagIds` 为去重的稳定标签 id，显示名来自 Git 中的公开标签字典；引用不存在的标签校验失败。热门标签从全部已发布文章的真实标签引用计数，按数量降序、同值 id 升序取前 10 项；无标签时隐藏，计数不包含推荐区的重复展示。
- `technicalKeywords` 只包含作者明确提供且与正文相关的技术词；`pullRequestRefs` 为 `{repository: owner/repo, number: 正整数, href: HTTPS}` 数组，链接指向真实对应 PR，不从示例编号或自由文本生成。搜索匹配标题、摘要、已提供作者的显示名、标签显示名、技术关键词，以及 PR 编号（纯数字或 `#数字`）和 `owner/repo#数字`；不索引文章全文或隐藏维护字段。
- 搜索摘要索引携带上述公开查询字段；同一篇文章即使多个字段命中也只返回一次。未提供作者、关键词或 PR 时省略对应字段，不能把缺失内容替换为团队名或示例引用。
- `cover` 仍使用 MediaSpec；可选 `preview: {src, width, height, alt, focalPoint?: {x, y}}` 保存经过确认的裁剪预览，焦点坐标为 0–1。推荐区 16:9、列表 3:2，允许 `object-fit: cover`；没有确认预览时对原图使用 contain 与中性衬底，不自动裁掉技术图中的文字或图例。正文图片与架构图始终保留完整固有比例，裁剪预览与原图一同接受来源、权限及资源校验。

正文允许标题 h2–h4、段落、列表、引用、表格、链接、图片、行内代码与围栏代码块。图示通过已登记的 DiagramFrame 数据引用；不接受原始 HTML、脚本、可执行 JSX、iframe 或内联样式。内容解析器必须执行允许项规则，而非把未知语法直接透传。

### 6.2 开发者文档

开发者文档采用 Git 中的普通 Markdown 与图片，文档标识、标题、导航顺序及适用产品版本由内容约定定义。部署类文档需覆盖前置条件、步骤、验证、故障排查与固定来源；不要求继承博客元数据字段，不要求作者维护 Guide JSON。

每个步骤说明目标、运行位置、命令、替换参数和预期结果；通过文档或仓库核验记录保存环境、日期、结果与证据。先有核验记录，再发布“可直接运行”的步骤。

- 本地体验与生产部署分别记录环境，不把模拟引擎结果当作真实 GPU 部署结果。
- 命令中的镜像、Chart 和依赖版本固定；升级版本后重新核验相关步骤。
- 密钥、域名和集群信息使用具名占位符，并说明填写位置；不使用真实用户凭据。
- 检查命令必须能验证部署和接口结果，不能只以“命令退出码为 0”判断模型可用。
- 可能改变集群资源的命令说明影响与适用环境；文档核验本身不授予在生产集群执行的权限。
- “10 分钟完成”等时间承诺要有测量环境与计时范围；证据不足则仅写操作步骤。

Docusaurus 负责侧栏、正文、标题目录、代码展示与自托管搜索。文档源 PR 合并后更新网站锁定 commit，经网站 PR 检查、全站构建和候选核验后统一发布；正文、图片和索引随同一网站镜像交付。当前没有真实文档，示例不得上线，不生成虚假的快速开始链接。

## 7 页面组合与外部资源

页面配置保存 meta、适用页面的 hero、区块开关与内容 id 引用；Article、Claim 的事实字段保存在 Git 文件；Catalog 事实保存源 id/版本引用；文档保存有效页面地址与 commit 引用。首页不配置文章推荐区，测评最多 4 条；博客推荐最多 1 篇、相关文章最多 3 篇，沿用页面契约。博客列表的页面标题保留可访问 h1，不强制额外可见 hero。

配置的默认测评、推荐文章及必填区块引用必须解析为所属来源的可公开记录；引用失效时校验报错，不能自动用另一条内容替换。未配置内容的条件区块可自然隐藏，但显式写错 id 属于错误。

社区资源的最小记录包括 `id`、`title`、`kind`、`href`、`description`、`checkedAt` 和来源；kind 为 repository / contribution / ecosystem / channel。生态协作说明另引用 Claim，不从单向技术兼容推导合作关系。

博客可选运营侧栏引用同一社区资源集合，不另建硬编码人数、群号或二维码。微信条目可选 `qr: MediaSpec`、经确认的 `contactLabel` 与 `contactValue`；二维码必须是已授权公开的入群或官方联系入口，旁边保留可读联系说明，不依赖扫码表达全部信息。知乎条目使用已核实的专栏 HTTPS 地址；关注数仅在同时提供来源和带时区 `observedAt` 时展示，标明统计时间，不自动刷新或假称实时。更新频率、入群赠品等宣传仅在有对应 Claim 时展示，缺少真实配置时整个卡片隐藏；侧栏来源随 Git 和网站版本交付。

门户 Footer 统一采用最新首页分组：开源代码（GitHub 仓库、Model Catalog 模型库）、社区与生态（博客洞见、微信开发者群、ModelHubXC 信创模盒）、开发者资源（技术文档）、法律与开源（Apache 2.0 License、Security Advisory、Roadmap 演进图、Code of Conduct）。博客入口只放社区组，避免原稿重复；目标未核实或未开放时使用明确的静态待开放文字，不编造地址或可用性声明。Header 和已实现文档 Footer 的既定例外见组件契约。

素材记录包含 MediaSpec 字段，以及来源、使用依据和必要署名。不得从设计占位图推定拥有品牌授权；Logo 必须使用用户提供或已明确可用的素材。

浅深素材可使用 MediaSpec.srcDark；替代图必须与主图表达同一信息并保持尺寸。Logo 不反色，截图不伪造夜间版本；无专用素材时使用中性外框，图表与受控 SVG 从语义色渲染。正文图片内容不因主题改变。

新稿中的 Live UI 曲线、性能数字、点赞、Star、健康状态、文章作者和部署命令均是待核验内容。监控截图只能作为标注版本的静态示意；无真实素材不输出模拟实时面板。Catalog 汇总提升需有可比较样本口径，不得跨模型、硬件和工作负载直接聚合。首页步骤只摘自有效快速开始，当前文档准备状态下不得补造命令。

草稿素材仅随受控预览提供；正式图片随 Git 提交和网站产物交付，通过本站地址提供。不得把 VPN 地址、临时签名 URL 或海外图床地址写进正式页面；不要直接覆盖公开的旧文件字节，采用内容 hash 管理资源并按撤回策略失效。

站内链接允许绝对站内路径与真实锚点，外部链接首期使用 HTTPS。禁止 javascript、data、file URL 作为导航或来源；外部图片地址同样不得嵌入私有令牌。已有 HTTP 资料需要替代来源或单独修订规则，不由生成器静默放行。

## 8 预览和发布校验

设计稿中的示例内容默认作为独立 fixture，使用 `example-` 前缀 id，与正式内容目录隔离。它不属于可发布的公共记录，不得通过修改草稿标记直接升级为真实数据。

网站不渲染全局“示例预览／仅供界面验证”提示条；文档 Mock 保留正文内的示例说明并与正式构建隔离。真实内容预览由外层预览界面显示“预览，未发布”及候选版本。两者均限制内网鉴权并设置不索引，不能只靠隐藏 URL 或 noindex 保护草稿。预览提示由外层预览界面提供，不写入待发布的候选正文。

网站正式产物仅包含选定 Git 提交中经检查确认的合格内容，排除 fixture、草稿、已撤回内容和审核元数据；检查范围包括 HTML、站点地图、搜索数据和客户端资源。撤回后的旧版本保留在私有归档；公开访问同步失效，不能因回滚归档仍保留就继续公开。

### 8.1 Markdown 编辑与文件接入

- 作者通过本地编辑器或 Git 托管平台编辑 `.md`；已有文章连同相对图片加入仓库，不提供后台上传或结构化表单。
- frontmatter 按白名单校验；包含稳定 id、标题、摘要、slug、日期、作者/分类/封面及来源等已定义字段。`draft` 只控制排除，不授予发布权限；禁止注入审核人、账号、命令或部署配置。
- Docusaurus 采用普通 Markdown 解析模式，并对 AST 检查；拒绝原始 HTML、JSX、import、执行表达式和不允许的 URL。不能依赖默认 MDX 编译器处理不受控内容。
- 相对图片须随提交存在且在允许的内容目录内；禁止越界路径和符号链接，不自动抓取任意 URL。文章 UTF-8 正文上限 2 MiB，单图上限 10 MiB；图片允许 PNG、JPEG、WebP，审核过的品牌 SVG 作为代码资源维护。
- frontmatter 与文章 DTO 显式映射：`description` 对应 summary，`date` 对应 publishedAt，显式 slug 对应 `/blog/{slug}`；不得默用日期路径。插件内置阅读时间关闭，沿用可选的有来源 readingMinutes。
- 外部文章以独立元数据维护，仅在列表链接原文，不交给博客正文插件生成空详情。
- 本地排版预览不等同于 PR 全站预览；正式发布以合并后的实际 SHA 和已验证候选为依据。

网站发布检查顺序：

1. 校验文件类型、元数据白名单、id、日期与文档来源 commit。
2. 校验内容引用、页面区块、默认项、排序字段及路由冲突。
3. 核对来源、比较公式、单位和口径；确认记录对应当前内容提交。
4. 暂存合格内容并构建完整网站，检查站内路由、锚点、图片和下载。
5. 核验必需外链；网络失败、权限错误或超时记为无法验证，不自动算通过。
6. 检查 HTML、搜索、RSS、站点地图与 JS 不包含草稿、fixture、撤回内容、私密素材或维护记录。

外链可达性和事实审查分开：HTTP 成功不表示内容支持声明；检查失败也不证明声明错误。当前发布批次的必需来源无法核实时，报告阻塞并保留线上旧版本，不能以删除断言或隐藏失败绕过。

不要求每次排版修改重跑所有 GPU 基准。模型、硬件、引擎、运行配置、工作负载或方法变化时产生新的测评版本并重新核验；只改措辞时核对其仍准确表达已有结果。

## 9 文案与变更规则

- 使用具体对象与条件，避免“所有模型”“永不中断”“行业最快”等无明确范围的绝对表述。
- 描述生产能力时同时给出适用环境与限制，不把目标 SLO 写成已达到的实际可用性。
- 发现错误数字或失效证据时修订或撤回对应记录，追踪所有引用页面；不能仅改首页而保留模型页旧数字。
- 内容撤回后清理默认项和推荐引用；原站内文章地址按页面契约返回 404，旧地址变更只在存在等价新内容时重定向。
- 审核记录、来源核对与内容修改保留版本历史；不冒用人员姓名，不伪造审核时间。

Catalog 由源系统校验并发布其数据，官网验证协议、来源和版本一致性；文档由 Git 检查内容、链接、素材与构建产物。门户、博客和文档统一构建发布，Catalog 数据独立更新；具体工作流遵循工程准则。
