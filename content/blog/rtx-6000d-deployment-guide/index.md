随着大模型推理逐步走向规模化部署，如何在满足推理需求的同时控制硬件投入，成了许多团队关注的问题。**我们选择 NVIDIA RTX 6000D 做适配入库，首先看中的就是它的性价比**：单卡具备 84GB 级别的显存容量，能够容纳更大的模型权重或更长的上下文，为成本敏感型的大模型推理场景提供了一个值得评估的硬件选择。

不过，性价比只是硬件选型的起点，要把这张卡真正用于实际部署，还需要跨过工程适配这一关。RTX 6000D 在算子支持、显存分配和多卡通信上都有具体要求；一旦更换模型、权重格式或推理引擎，相关配置就需要重新核对和调整。

为此，ModelSphere 针对 DeepSeek、GLM 与 Kimi 的多组权重和引擎组合逐一完成适配，整理出对应的 RTX 6000D 部署配方。每份配方都保留了适用组合所需的引擎镜像、卡数与节点要求，以及计算后端、并行布局和显存参数。

接下来，文章将从适配过程中遇到的启动与计算问题讲起，带你了解这些配置是如何确定的，再结合六组长文本实测数据，看看不同部署组合的实际运行表现。如果涉及多机部署，后文也整理了 PD 分离的配置要点与 RoCE 链路排查经验，方便对照参考。

## 01 从启动到响应，先确认模型跑得起来、算得正确

在正式调整模型参数之前，先要摸清硬件本身的特性，并确认服务既能正常启动，又能输出准确结果。

### 本次实践的硬件环境

本次部署环境每台服务器配备 8 张 RTX 6000D，计算能力标识为 `sm120`，单卡实际可见显存为 85,651 MiB（约 83.6 GiB）。这 8 张卡之间通过 PCIe 互联，没有 NVLink。

这两项硬件特征决定了后续的配置边界：单卡显存容量决定了权重、KV 缓存和临时工作区一共能分到多少空间；卡间 PCIe 带宽则影响多卡协同中的数据交换。采用张量并行（TP）时，GPU 之间需要频繁交换和汇总中间结果，因此并行规模也要结合 PCIe 带宽来评估。

由于缺少 NVLink，推理引擎中面向 NVLink 拓扑设计的 `custom all-reduce` 通信路径（依赖 GPU 间 P2P 直写对端显存）在本次环境中因拓扑和 P2P 条件受限而停用，多卡通信回退到 NCCL。排查通信表现时，可以先看启动日志里最终启用的通信后端，再结合设备拓扑进一步检查；具体启用条件以对应引擎版本的实现为准。

### 卡在 warmup：先分清是算子适配问题，还是显存空间不足

权重加载完成后，引擎还会进入预热（warmup）和执行准备阶段。在 vLLM 上，我们遇到过两类导致启动停在这一阶段的故障，虽然都发生在权重加载之后，但成因和处理方向不同：

| 故障现象与原因                                                                                  | 对应处理方向                                                                       |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 部分融合 MoE 算子在执行 autotune（自动调优）时，尝试了未针对 `sm120` 构建的 shape，导致启动停滞 | 按对应模型配方关闭 FlashInfer autotune，或仅跳过相关融合算子，保留其余自动调优能力 |
| 权重已加载完毕，但预热阶段申请临时 workspace 时显存不足（其中一次记录的额外需求约为 1.5 GiB）   | 重新核算权重之外的显存分配，调整 KV 缓存池、激活值与预热工作区的空间预算           |

遇到启动停滞时，先从日志确认引擎具体停在哪个阶段，再结合显存余量信息，就能判断应该调整算子适配项，还是重新分配显存预算。

### 启动之后，用固定题目做一轮重复回归

服务拉起、健康检查通过之后，还需要验证实际生成结果是否准确——比直接报错更隐蔽的风险是「静默算错」。我们在实测中遇到过简单算术题答错、输出数字碎片的情况；直接查看接口的原始返回文本，看到的也是同样的异常内容，说明问题出在前向计算本身。进一步排查后发现，异常出现在某条特定的量化计算路径上，而同一算子库的其他路径在所测组合中能够正常运行。

针对这类计算异常，我们采用了一组基础回归检查：挑选几道答案明确的题，将 `temperature` 设为 0，在低并发下逐题串行重复请求，同时直接查看原始返回文本。

每当更换模型、权重格式、引擎版本或计算后端时，我们都会重跑一遍这组检查。因为推理引擎可能根据硬件能力和权重格式自动选择底层计算算子（kernel），命令行参数里未必显式体现，因此验证需要覆盖实际运行的模型、权重与引擎组合。

检查时主要关注两类结果：

- **答案明显错误或文本损坏**：继续核对权重文件、加载方式、计算路径与输出处理，结合对照实验定位根因。
- **同一输入多次输出不一致**：先记录出现条件，再排查批次组成与计算确定性。`temperature=0` 固定了贪心采样策略，但底层前向计算仍可能随并发批次变化产生差异，这也是建议在低并发下串行测试的原因，具体机制可参考 [vLLM 批次不变性说明](https://docs.vllm.ai/en/latest/features/batch_invariance/)。

这组回归用于尽早发现明显的计算异常；完整的模型生成质量，仍需结合对应任务集和目标上下文长度单独评估。

## 02 按模型与引擎选配方，把关键适配项对上

ModelSphere 已将本次在 RTX 6000D 上验证并运行过的六组模型整理为部署配方。选用时，先对齐目标模型与权重格式，再确定 SGLang 或 vLLM 引擎，最后核对卡数、节点数和并行布局。

下表汇总了这六组组合的运行形态与关键适配项；完整的镜像地址、启动参数与资源要求见各自对应的配方文件：

| 模型                         | SGLang          | vLLM          | 关键适配项                                                                              |
| ---------------------------- | --------------- | ------------- | --------------------------------------------------------------------------------------- |
| DeepSeek-V4-Flash            | TP4／TP8        | TP4／TP8      | vLLM：KV block size 设为 256                                                            |
| DeepSeek-V4-Flash-0731-NVFP4 | TP4／TP8        | TP4／TP8／PD  | SGLang：采用 Marlin；vLLM：关闭 autotune，KV block size 设为 256                        |
| DeepSeek-V4-Pro              | TP8 × PP2       | TP8 × PP2     | vLLM：KV block size 设为 256，跳过特定 autotune 算子                                    |
| GLM-5.2-NVFP4                | TP8 × PP2 × EP8 | TP8 × PP2     | SGLang：启用 EP8 并指定对应量化格式；vLLM：跳过特定 autotune 算子                       |
| GLM-5.3-NVFP4                | TP8 × PP2 × EP8 | TP8 × PP2／PD | SGLang：启用 EP8、指定对应量化格式，静态显存比例设为 0.72；vLLM：跳过特定 autotune 算子 |
| Kimi-K3                      | TP8 × PP4       | TP8 × PP4     | SGLang：采用 Marlin；vLLM：关闭 autotune                                                |

表中涉及几项并行缩写：`PP` 是流水线并行，把模型按层切分到多个计算阶段；`EP` 是专家并行，将 MoE 架构中的不同专家分配到各自进程；`PD` 是将处理输入的 prefill 与逐 token 生成的 decode 拆开部署，后文第 05 节会继续展开。

表中的适配项按具体模型逐行给出，因为不同模型和引擎在分页大小、计算后端与切分方式上各有具体约束。

### KV 分页大小，需要与注意力路径匹配

本次 DeepSeek 系列的 vLLM 配方统一配置了 `--block-size=256`，用于控制 KV cache 的分页大小。在所测稀疏注意力索引器路径上，实测填入 64 或 128 都在 worker 初始化阶段直接失败，其中一次表现为除零错误，报错信息中并未直接指出 block size。

遇到这一组合的初始化失败时，可以先核对配方要求的分页大小，再结合报错继续排查。需要注意的是，256 对应本次测试的模型与注意力实现，其他模型仍应遵循各自配方的设置。

### 同样是 NVFP4，计算后端与切分方式需按模型分别匹配

即便权重格式同为 NVFP4，不同模型在同一引擎下的适配路径也有差异。例如在 SGLang 中，DeepSeek-V4-Flash-0731-NVFP4 使用 Marlin 路径，而 GLM-5.3-NVFP4 的对应路径则使用 FlashInfer CUTLASS——测试中 GLM 的一次失败直接发生在 MoE 权重加载器中，需要先解决加载与切分匹配问题，之后才能进入算子计算。

切分方式同样如此。在本次 SGLang + GLM NVFP4 组合中，纯 TP 切分曾出现两倍关系的 shape 冲突。对应配方通过 `EP8` 将专家分配到不同进程，并指定 `modelopt_fp4` 量化格式；其中 GLM-5.3 还将 `--mem-fraction-static` 设为 `0.72`，为后续启动过程留出空间，完整参数见 [GLM-5.3 对应配方](https://github.com/modelsphere/model-catalog/blob/c7219f9091937890ed54f547af94639e26310920/models/glm5.3/sglang-tp8-pp2-ep8-6000d.yaml)。

面对新的组合时，先对齐具体的模型、权重格式与引擎版本，再核对后端、并行方式与显存参数，能更快缩小排查范围。

### 多机并行策略：本次采用单机 TP、跨机 PP

对于多机部署的模型，本次双机配置采用 `TP8 × PP2`，四机配置采用 `TP8 × PP4`，将张量并行（TP）保持在单台服务器内，跨机扩展使用流水线并行（PP）。

这一布局同时考虑了 PCIe 通信开销与量化权重的加载限制。一方面，卡间走 PCIe，跨机扩大 TP 会增加集合通信开销；另一方面，测试中部分 FP4 权重在 `TP16` 切分下出现了维度相差两倍的 shape 错误，涉及量化权重的打包布局与切分粒度匹配。因此，本次将 TP 保持在单机 8 卡内、跨机采用 PP，并按各流水线阶段的资源需求配置通信与执行。后续评估新的权重或引擎版本时，仍需重新确认加载器支持情况与实际网络带宽。

## 03 显存预算要算到预热、图捕获和实际运行

选好 ModelSphere 中的模型配方后，落到具体机器上时还需要核对显存设置。一张显卡上除了常驻的模型权重，还要同时容纳 KV 缓存池、激活与临时工作区，以及 CUDA Graph 图捕获等执行机制带来的额外占用。

以约 430 GiB 的模型权重为例，粗略均摊到单机 8 张卡上，每卡权重约占 54 GiB。在 RTX 6000D 约 83.6 GiB 的可见显存中，留给其余部分的空间不足 30 GiB。实际分片会随并行布局变化，前期规划时可以用下面的关系式做初步估算，再结合各执行阶段的峰值和运行日志校正预算：

`KV 缓存 + 激活及临时工作区 + 图捕获等额外占用 < 可用显存 − 每卡权重`

### 同一个显存比例，换硬件后要重新核算

常见的显存参数（如 `0.85`、`0.90`）设置的是**比例**，而权重之外要放入剩余空间的图捕获、预热工作区等占用则是相对固定的**绝对容量**。换用单卡容量不同的 GPU 时，即使沿用同一个比例，留给这些固定开销的绝对空间也会明显变化。

在本次对照中，同一模型在 288 GiB 显存设备上设置 `0.85` 可以正常运行，放到 RTX 6000D 上时，相应的 SGLang 组合需要将静态显存比例降到 `0.72`。此外，SGLang 的 `mem-fraction-static` 与 vLLM 的 `gpu-memory-utilization` 预算覆盖范围也有区别，调参时应将数值与引擎本身的含义一起看。

**CUDA Graph 捕获阶段也需要单独观察。** 我们曾连续下调三档静态显存比例，引擎仍在捕获阶段因显存不足而退出；另有一次记录显示，捕获相关占用约为 6.5 GiB。实际需求会随捕获配置和执行阶段变化，调整时应同时检查三件事：图捕获能否完成、KV 缓存池还剩多少容量，以及加载目标负载后是否留有余量。下调静态显存比例会减少可用于 KV 池的空间，找到能够完成启动并承接目标负载的设置后即可停下，再继续评估上下文长度和并发能力。

### 多机启动后异常退出，直接看失败 worker 的日志

多机部署时，这一阶段的退出现象容易让人误判：我们曾遇到引擎在权重加载完成约 40 秒后退出的情况，主进程所在的 leader 节点日志里只记录了子进程退出信号，具体的错误堆栈（traceback）实际出现在失败的 worker 节点日志中。

遇到类似现象时，建议先沿各 worker 节点的日志确认失败阶段，再检查图捕获结束后的剩余显存。如果服务顺利通过启动、加上负载后才出现分配器 OOM 告警，就需要继续调整显存分配与并发数。

## 04 六组长文本实测：这些模型在 RTX 6000D 上表现如何

确定了部署配置与显存预算后，接下来看这些模型在对应并行布局下的推理表现。

下面这六组性能数据均使用 **vLLM** 测试，采用统一的长文本负载口径：单请求 **50K token 输入、1.5K token 输出**，**并发 30**，持续 **600 秒**；请求发送至 `/v1/completions`，以 token ID 控制输入长度；测试期间**前缀缓存命中率为 0%**，反映未获得前缀缓存复用加成时的表现。各模型的参数规模、权重格式与部署卡数不同，两组表格用于对应配置下的部署参考。

### 整体处理量

| 模型                         | 部署规模              | 输入吞吐 tok/s | 输出吞吐 tok/s | 总吞吐 tok/s |
| ---------------------------- | --------------------- | -------------: | -------------: | -----------: |
| DeepSeek-V4-Flash-0731-NVFP4 | 单机 8 卡，TP8        |          9,892 |          272.7 |       10,164 |
| DeepSeek-V4-Flash            | 单机 8 卡，TP8        |          7,734 |          209.8 |        7,943 |
| GLM-5.2-NVFP4                | 双机 16 卡，TP8 × PP2 |          5,455 |          128.2 |        5,584 |
| DeepSeek-V4-Pro              | 双机 16 卡，TP8 × PP2 |          5,395 |          160.1 |        5,556 |
| GLM-5.3-NVFP4                | 双机 16 卡，TP8 × PP2 |          5,335 |          144.3 |        5,480 |
| Kimi-K3                      | 四机 32 卡，TP8 × PP4 |          4,976 |          108.3 |        5,084 |

表中的总吞吐为输入吞吐与输出吞吐合计。在本次 50K 输入、1.5K 输出的长输入负载下，输入处理量占主要部分；回答生成的快慢则结合下一张表中的首字等待与单请求输出速度观察。各列沿用原始记录的取整值，分项之和与总吞吐之间可能有小幅取整尾差。

### 单请求表现

| 模型                         | 首 token 延迟 TTFT | 单请求输出速度 | 总吞吐折算每卡 tok/s |
| ---------------------------- | -----------------: | -------------: | -------------------: |
| DeepSeek-V4-Flash-0731-NVFP4 |             6.4 秒 |     10.2 tok/s |                1,271 |
| DeepSeek-V4-Flash            |             5.7 秒 |      7.7 tok/s |                  993 |
| GLM-5.2-NVFP4                |            67.2 秒 |      5.3 tok/s |                  349 |
| DeepSeek-V4-Pro              |            12.0 秒 |      5.3 tok/s |                  347 |
| GLM-5.3-NVFP4                |            36.7 秒 |      5.3 tok/s |                  343 |
| Kimi-K3                      |            14.2 秒 |      4.4 tok/s |                  159 |

这里的 `TTFT` 统计从提交请求到首个输出 token 返回的等待时间；每卡吞吐是整组总吞吐除以所用卡数的折算值，衡量当前多卡部署下的平均每卡处理量。

结合两张表可以看到，整体处理量与单请求响应需要分开权衡：两个 Flash 组合在并发 30 下 TTFT 分别为 6.4 秒和 5.7 秒，单请求输出速度分别为 10.2 和 7.7 tok/s；而 GLM-5.2 与 GLM-5.3 在相同并发下，首字等待分别达到 67.2 秒和 36.7 秒，进一步提高并发前，应先检查排队情况与可用容量。

本次实践也记录了后续复测时的并发起点供参考：

- **DeepSeek-V4-Flash 两个版本**：并发 30 时仍有余量，可继续探索 30 以上；
- **DeepSeek-V4-Pro**：可从约 30 并发开始评估；
- **GLM-5.2-NVFP4 / GLM-5.3-NVFP4**：建议分别从约 20 和约 24 并发开始测试；
- **Kimi-K3**：侧重整体处理量时可参考 30 并发，侧重交互响应时从 16 并发开始评估。

**需要注意，表内指标统一测自并发 30；调整并发后，首字延迟与输出速度需要重新测量。** 选用配置时，建议将目标输入输出长度、可接受的等待时间与模型任务质量放在一起判断。

## 05 采用 PD 分离时，先配好两侧资源与 KV 传输

当业务负载呈现「长输入、短输出」特征且 prefill 压力较大时，可以进一步评估 PD 分离架构——将处理输入上下文的 prefill 与逐 token 生成的 decode 放到不同实例，让两侧独立调整实例数量。

拆分部署会增加 router 组件和跨机 KV 传输链路，两侧的资源配比也需要与负载匹配。在一次 prefill 密集型负载的对照中，将 prefill 组减半、decode 保持不变，每卡吞吐下降约两成，首字延迟约翻倍。因此在采用 PD 分离前，需要先摸清请求的输入输出比例和实际瓶颈。

### 两个与 KV 传输直接相关的设置

- **显式指定 KV 传输使用的 RDMA 网卡（HCA）。** 如果两侧自动选择到彼此不可达的设备，故障表现容易造成误导：实测中握手显示成功、没有明显的 RDMA 报错，随后双方却互报对端失效。在 SGLang 的对应路径中，可通过 `--disaggregation-ib-device` 指定设备，配置需与所用传输后端和引擎版本匹配。
- **按传输实现选择内存分配方式。** 本次测试中，KV 传输在注册由 `expandable segments` 分配的显存时出现了「地址无效」错误，因此对应的 PD 配方将内存分配器参数设为 `expandable_segments:False`。TP／PP 集合通信使用通信库自己的缓冲区注册路径，需要按对应实现另行核对。具体传输要求可参照 [SGLang PD 文档](https://docs.sglang.io/docs/advanced_features/pd_disaggregation)。

### 路由与缓存行为，上线前逐项验收

以下是本次所用 router 与引擎组合中遇到的行为特征；由于路由和引擎实现仍在演进，升级版本后需重新核对：

| 验收环节 | 本次观测现象与对应做法                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 输入格式 | router 收到 token ID 形式的 prompt 后返回 `422`。通过该入口压测时，需改为发送文本请求并自行标定 token 数。                           |
| 诊断返回 | router 未透传响应中的 token ID；绕过 router 直连引擎时，请求又会因缺少握手信息被拒绝。开展诊断测试时，请求方式需与实际调用路径匹配。 |
| 指标采集 | router 未代理引擎的 `/metrics` 接口，直接请求返回 `404`。监控应直接从引擎端口采集指标。                                              |
| 后端重启 | decode 实例重建时，曾导致 router 存活探针失败并重启，直到后端恢复。排查异常时需对照 router 与引擎两侧日志的时间线。                  |
| 分层缓存 | 本次测试的 decode 组合不支持所用的主机内存分层缓存配置。开启前需按引擎版本与缓存模式确认支持范围及配置位置。                         |

## 06 跨机走 RoCE，按设备、路径与链路逐层排查

本次多机环境使用 RoCE（基于以太网的 RDMA），每台服务器连接多条独立的 400G 网络链路（rail）。在相应网络与执行路径下遇到跨机通信问题时，可以按下面的顺序逐层排查：

**第一步，确认容器能否正常访问 RDMA 设备。** 我们在测试中曾遇到容器在独立 Pod 网络命名空间下读出的 GID（全局标识符）表全为 0 的情况，随后通过为推理 Pod 配置 `hostNetwork` 处理了这一设备访问问题。排查时先确认容器内的设备与网络命名空间，再检查 RoCE v1／v2 和 GID 的选择。

**第二步，分别为集合通信与 KV 传输指定高速网卡。** 宿主机上的管理网口也可能进入候选列表，但它与 400G 高速计算网络分属不同网络，跨机计算流量应显式指定高速网卡。NCCL 集合通信通过 `NCCL_IB_HCA` 选择网卡，SGLang 的对应 PD 路径则使用前述引擎参数；同时建议核对 GPU 与网卡的 PCIe 亲和关系，减少绕行。

**第三步，遇到偶发变慢或超时，先检查物理链路。** 我们曾遇到某个端口的单条物理通道（lane）异常，表现为间歇性的链路翻动（flap）。查看网卡的 `carrier changes` 计数，并结合端口错误、丢包与速率统计，有助于定位这类物理层问题。

**第四步，确认 GPU Direct RDMA 的 PCIe 路径。** 普通 RDMA 与 GPU 到网卡的直接通信需要分开检查。开启 PCIe ACS 重定向可能将点对点流量绕行到 root complex，造成性能退化或通信挂起。本次环境中机器重启后 ACS 设置曾恢复为此前的状态，因此重启后需要重新检查；裸机和虚拟化环境的处理方式按各自要求选择，详见 [NVIDIA GPU 通信排障说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/gpu_troubleshooting.html)。
